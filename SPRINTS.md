# REVA Engineering Progression

## Purpose

This document records REVA's completed engineering milestones and the next approved milestone. It is the project-history counterpart to `AGENTS.md` (durable engineering law), `REVA_BUSINESS.md` (business/content decisions), and `DATA_ARCH.md` (current approved data architecture). It is not a source of runtime behavior or a substitute for migrations and code.

Every completed Sprint was validated within its approved scope. Later work may replace an earlier implementation boundary without invalidating the historical milestone that established it.

## Completed Sprints

### Sprint 0 — Project Initialization

Established the official Next.js App Router project with TypeScript, Tailwind CSS, ESLint, `src/`, pnpm, and the default import alias. The project builds and lints through pnpm.

Removed the default example experience and established the initial folder, metadata, global-style, and minimal-placeholder foundation.

### Sprint 11 — Backend Architectural Foundation

Established provider, service, and infrastructure boundaries without coupling REVA's business architecture to a database provider or implementing business queries.

Added the official Supabase tooling and request-safe infrastructure boundary, then standardized public routes in Spanish. Public Product URLs are canonical at `/productos/[slug]`; Collections are architecturally reserved for `/colecciones/[slug]`.

### Sprint 13 — Data Model Approval

Finalized the conceptual domain model and created `DATA_ARCH.md`. The key distinction is permanent: an Intake Item is a received physical garment; a Product is REVA's unique selling opportunity derived from at most one Intake Item.

### Sprint 14 — Production Schema and Authorization Foundation

Created, locally validated, and remotely applied Migration 001 (schema and integrity) and Migration 002 (default-deny RLS and authorization). The schema is versioned and Supabase is used only as infrastructure; normal application access preserves the caller's RLS context.

### Sprint 15 — TypeScript Domain Alignment

Aligned domain contracts, service boundaries, repositories, money handling, condition mapping, Intake, Tags, Collections, Profiles, Marketing Preferences, and Testimonials with the approved persisted model. Database-generated types remain infrastructure-only.

### Sprint 16 — Authorization Design and RLS Validation

Completed the authorization matrix, hardened the RLS auto-enable helper into the private schema, confirmed conservative deletion rules, and validated local adversarial access scenarios before remote deployment.

### Sprint 17 — Supabase Security Context Design

Defined the four request contexts: public visitor, authenticated customer, authenticated admin, and privileged infrastructure. The project intentionally avoids using a privileged credential as a normal repository shortcut.

### Sprint 18 — Authentication and First Admin Bootstrap

Implemented email/password authentication with email confirmation, cookie-backed SSR sessions, request proxy refresh, logout, automatic customer Profile provisioning, `SupabaseProfileRepository`, and the controlled first-admin bootstrap. ### Sprint 21 — Product Media Pipeline

Created and remotely applied Migration 007, establishing the private `product-media` Storage boundary and admin-only Product Image metadata operations. Product media is processed only in the trusted Node boundary: source JPEG/PNG is auto-oriented, resized without upscaling, stripped of metadata, encoded as WebP, stored privately, and represented through ordered Product Image metadata. Original source files are not retained in Supabase.

No Product was published, no public Catalog or Product Detail presentation changed, and draft media remains inaccessible to anonymous visitors and customers.

### Secure purchase-request and transactional Checkout architecture discovery (2026-10-14; proposal only)

**Scope/status:** The developer approved the future high-level direction `PDP or Cart → shared Checkout → securely submitted purchase request → WhatsApp coordination → externally hosted payment link → trusted payment verification → fulfillment`. The architecture below is a proposal awaiting explicit architecture/business/security approval; it is not implementation authorization. The current `/checkout`, Cart, PDP conversion, and privacy statements remain non-transactional: the browser stores only Product slugs in Cart, form values stay in memory, and REVA currently receives/stores no Order, address, phone, billing identifier, payment, reservation, or FEL data. No code, migration, provider setting, Product, real customer data, or deployment was changed.

**Existing vs proposed behavior:** PDP `Comprar ahora` continues to enter the shared Checkout with one Product; `Agregar al carrito` stays separate; Cart continues to enter with its selected Products. The proposed final action is **“Solicitar compra por WhatsApp”**, with an explicit disclosure that submission is a purchase request, availability/delivery/payment are subject to confirmation, and opening WhatsApp does not confirm a sale or message delivery. Preserve a secondary general WhatsApp inquiry where appropriate. Remove/repurpose the legacy PDP **“Comprar por WhatsApp”** purchase shortcut only in a separately approved implementation so it cannot bypass Checkout. Proposed copy for review: “Por el momento, las compras en REVA se coordinan por WhatsApp mediante un enlace de pago. Tu compra estará sujeta a confirmación de disponibilidad, envío y pago.” Do not present the proposed sentence as a finalized legal or shipping policy.

**Proposed minimal model (no tables approved):**

- `orders` (or one equivalently named purchase-request aggregate): an internal UUID; cryptographically random, non-authorizing customer-facing reference; one lifecycle state; GTQ currency; immutable amount snapshot; `created_at`, `updated_at`, and database-owned hold expiry; a durable idempotency-key digest; required Terms version/hash and acceptance timestamp; and the Privacy notice version shown/acknowledged where qualified review determines that acknowledgement is appropriate. Do not create separate request and Order rows with duplicated snapshots unless a separately identified business state requires both. A request/order record before verified payment is explicitly not a completed sale.
- `order_items`: immutable Product UUID reference plus verified SKU/title/condition/unit-price snapshots and quantity `1`. Resolve every fact server-side from the locked authoritative Product row at submission, not browser text, public projection price, or caller-provided SKU. If any selected Product is no longer published/available or its price differs from the shopper's reviewed price, reject the entire submission, return current safe facts for renewed review, and do not create a partial request/hold.
- `inventory_reservations`: auditable one-Product/one-request holds, with a database-enforced uniqueness rule permitting at most one active hold per Product; server/database timestamps and status; and deterministic release/expiry. Create all holds for a multi-item request atomically or none. Coordinate this new operation with the existing `draft/published/reserved/sold/archived` lifecycle and guarded Product RPC/M016 invariants; never write lifecycle fields directly from UI or a generic repository.
- Separately protected contact, delivery, and conditional billing payloads. Keep municipality/zone operational codes distinct from full delivery directions so codes can be validated against controlled references; any code linked to an individual Order is still access-controlled personal data. Encrypt free-form street/building/delivery references, contact values, and any collected NIT/CUI/name-to-invoice as separate purpose-bound payloads; do not collect invoice fields until tax review establishes the need. Keep payment records separate from Orders. An append-only `order_events`/audit record is a proposed minimum for actor, action, object reference, and timestamp, without plaintext PII or secrets.

**Request and Order lifecycle proposal:** one server-authoritative submission validates and normalizes the bounded request, verifies the current Terms/Privacy versions, re-resolves all Products/prices, and performs an all-or-none transaction that snapshots lines, records the request, establishes holds, and stores the idempotency result. The three-hour hold proposal starts at the database timestamp when that transaction commits successfully—not on PDP/Cart/Checkout entry, button rendering, or WhatsApp launch. The `expires_at` is immutable absent an explicitly approved, audited extension policy. The customer receives a request reference and WhatsApp handoff only after successful commit; if a race is lost, show which items need renewed selection without retaining the submitted PII. The hold clock means REVA operations must confirm serviceability/shipping and coordinate the payment link before expiration; otherwise the reservation expires and inventory is released. This operational consequence is a blocking business decision.

Use separate order, reservation, payment, and fulfillment states rather than one overloaded status. Conceptual order progression: `request_received → awaiting_payment_link/awaiting_payment → paid_verified → fulfillment → fulfilled`; terminal/exception states include `cancelled`, `expired`, `payment_failed`, and `refund_required/refunded` only after refund rules and provider operations are defined. Payment remains pending until trusted verification; browser return pages, customer screenshots, WhatsApp claims, and a link click are not proof. A late payment after hold expiry must never silently fulfill or reacquire stock: reconcile provider state, atomically check whether the Product remains available, otherwise route to an approved refund/manual-resolution path. Define race ownership, cancellation, retry, and recovery actions before launch.

**WhatsApp specification:** Generate the prefilled message from the committed request server-side and send it only to the already configured official WhatsApp destination. Include the random public request reference, verified Product title, internal SKU resolved only in the secure server/database transaction, current verified unit price, merchandise subtotal, “envío pendiente de confirmación,” and a request to coordinate the hosted payment link. Do not include PDP URLs, internal UUIDs, full name, phone, address, municipality/zone, NIT/CUI, card/payment credentials, or other PII in the WhatsApp URL. The reference is an identifier, never an authorization credential. Keep the existing public projection SKU policy unchanged; do not broaden public projections just for this message. WhatsApp remains an external processor/channel and a user action, not evidence that REVA received a message.

**Encryption/key custody proposal:** use maintained server-side Node cryptography with authenticated encryption (AES-256-GCM is a candidate, not custom crypto), a cryptographically secure unique nonce per encryption, and a format/key identifier for decryption and rotation. Bind ciphertext with authenticated additional data to the order UUID, field purpose, and format version to reduce cross-record/field substitution. Store ciphertext, nonce, authentication tag, format version, and key ID—not plaintext—in the database; do not use deterministic encryption or indexes that expose address/NIT values. Encrypt only fields needing confidentiality; preserve normalized FK/unique/operational integrity fields separately where required. Keep keys outside Supabase/database, client bundles, logs, and source control; prefer a managed key service/envelope-encryption boundary if an approved host/provider can support it. Do not assume Render environment variables are a KMS. Before selection, define active/previous-key rotation, compromised-key response, access audit, backup restoration with matching key versions, re-encryption and cryptographic-erasure behavior. AES-GCM protects ciphertext integrity/confidentiality at rest but not a compromised app process, authorized plaintext access, screenshots, or logs after decryption. OWASP recommends authenticated modes, separation, tested key lifecycle/rotation, and minimizing stored sensitive data. [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html), [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet).
